## 1. Резюме

Система функционально богатая и в целом аккуратно написанная, но **в текущем виде небезопасна для production и частично неработоспособна «из коробки»** — то есть ровно в том сценарии, который описан в README.

Ключевой вывод: **три независимых дефекта конфигурации приводят к полной компрометации или неработоспособности** при простом следовании инструкции README:

1. JWT подписывается **публично известным секретом** из `_env.example` (`change-me-in-production`), потому что проверка «сильного» секрета сравнивает строку только с одним конкретным значением.
2. Демо-аккаунты с паролем `123456` (включая диспетчера МЧС) создаются **даже в production**, так как в поставляемом `.env` явно задано `SEED_ON_STARTUP=true`.
3. `YOLO_WEIGHTS=` (пустая строка) **отменяет** дефолтный путь к весам, поэтому нейросеть не загрузится никогда — даже если положить файл туда, куда велит README.

Дополнительно: **вся тяжёлая работа по инциденту выполняется синхронно внутри async-эндпоинта**, что останавливает обработку всех остальных запросов и WebSocket-оповещений на секунды–минуты (фактически self-DoS).

## 3. 🔴 Критические дефекты (P0)

### P0-1. JWT подписывается публично известным секретом в production

**Где:** `backend/app/main.py:32`, `backend/app/main.py:59-60`, `_env.example:4`, `.env`

```python
SECRET = os.getenv("SECRET_KEY", "dev-secret-change-me")        # :32
...
if PROD and SECRET == "dev-secret-change-me":                    # :59
    raise RuntimeError("Set a strong SECRET_KEY when APP_ENV=production")
```

Проверка сравнивает секрет **ровно с одной строкой**. Поставляемый `_env.example` (и, соответственно, `.env`, который README велит скопировать) содержит:

```
SECRET_KEY=change-me-in-production        # 23 символа
```

**Последствия.** Пользователь, который «правильно» выставляет `APP_ENV=production` и не меняет `SECRET_KEY`, получает работающий сервер, подписывающий токены ключом, опубликованным в репозитории. Любой человек может выпустить себе токен:

```python
jwt.encode({"sub": "2", "exp": ...}, "change-me-in-production", algorithm="HS256")
```

`sub` — это просто `id` пользователя (`main.py:102`), а `id` диспетчера МЧС тривиально предсказуем. Это **полный захват роли MCHS**: удаление инцидентов, PDF-донесения, сканирование RTSP (SSRF), критичные уведомления.

**Дополнительно:** README утверждает, что при `APP_ENV=production` нужен `SECRET_KEY` длиной >20 символов — **такой проверки в коде нет вообще** (`grep` по `SECRET` даёт только строки 32, 59, 60, 102, 146). `change-me-in-production` — 23 символа, то есть формально «проходит» даже заявленное правило.

**Исправление:**
- Список запрещённых значений: `{"", "dev-secret-change-me", "change-me-in-production", "changeme", "secret"}` и/или проверка энтропии/длины (`len(SECRET) >= 32`).
- Падать при `PROD`, если `SECRET_KEY` не задан **или** слабый.
- Отдельная проверка на старте: печатать предупреждение, если секрет совпадает с примером.

### P0-2. Демо-аккаунты с паролем `123456` создаются в production

**Где:** `backend/app/main.py:61`, `backend/app/seed.py:12-16,64-70`, `.env`, `_env.example:37-38`

```python
if os.getenv("SEED_ON_STARTUP", "false" if PROD else "true").lower() == "true":   # :61
    seed()
```

Задумка верная: дефолт зависит от `PROD`. Но в поставляемом `.env` стоит **явное** `SEED_ON_STARTUP=true`, которое перекрывает дефолт. А `SEED_PASSWORD=123456`.

**Последствия.** Пользователь, который выполнил `cp _env.example .env` и выставил `APP_ENV=production` (единственное действие, которое README называет обязательным), получает на боевом сервере три учётные записи:

| Роль | Email | Пароль |
|---|---|---|
| Лесничий | `forester@kedr.ru` | `123456` |
| **Диспетчер МЧС** | `mchs@kedr.ru` | `123456` |
| Гражданин | `citizen@kedr.ru` | `123456` |

Комментарий в `_env.example` при этом прямо утверждает обратное: «production: требует SECRET_KEY, **не сидит демо-пользователей**». Это ложь относительно поведения кода.

Усугубляется тем, что в UI (`frontend/src/App.jsx:51`) есть кнопки автозаполнения с этими кредами — они рендерятся **вне зависимости от `APP_ENV`**.

**Исправление:**
- В `PROD` игнорировать `SEED_ON_STARTUP` и/или требовать отдельный `DEMO_SEED_CONFIRM=I_UNDERSTAND`.
- Отказываться стартовать, если `PROD` и `SEED_PASSWORD` слабее N символов.
- Убрать кнопки демо-входа из production-сборки (флаг сборки `VITE_ALLOW_DEMO`).

### P0-3. Пустой `YOLO_WEIGHTS` полностью ломает загрузку модели

**Где:** `backend/app/services.py:37-39`, `backend/app/main.py:45,685`, `.env`, `_env.example:9`

`.env` и `_env.example` содержат:

```
YOLO_WEIGHTS=                 # пустое значение, НЕ отсутствие переменной
```

```python
path = os.getenv("YOLO_WEIGHTS", "weights/yolov8x-fire.pt")   # services.py:37
if not os.path.exists(path):
    raise RuntimeError(f"Model weights not found at {path}. Train first: ...")
```

Поскольку переменная **присутствует** (Docker Compose передаёт её как пустую строку), `os.getenv` возвращает `""`, а не дефолт. Проверено инструментально:

```
YOLO_WEIGHTS env value      : ''
os.getenv('YOLO_WEIGHTS',d) : ''      <-- дефолт НЕ применён
os.path.exists(path)        : False
=> get_model() would raise  : True
```

**Последствия:**
- README **Вариант Б** («положи `yolov8x-fire.pt` в `backend/weights/`») **не работает** — приложение всё равно ищет `""`.
- `/health` всегда возвращает `model: false` (`main.py:685`), `/analyze` всегда 503.
- README **Вариант А** тоже не работает: `ensure_weights` (`main.py:45-47`) выходит по `if not url` — `YOLO_WEIGHTS_URL` в поставке тоже пуст, хотя README утверждает, что он «уже прописан по умолчанию».

Итог: **детекция огня не работает ни при каком следовании документации**, а сообщение об ошибке отсылает к несуществующей команде (см. P2-9).

**Исправление:** читать `os.getenv("YOLO_WEIGHTS") or "weights/yolov8x-fire.pt"`; убрать пустые значения из примеров или задать реальный URL/путь по умолчанию.

### P0-4. Блокирующие сетевые вызовы внутри async-эндпоинта замораживают весь API

**Где:** `backend/app/main.py:247-327` (`enrich`), `backend/app/services.py:402-432` (`get_terrain_type`), `backend/app/services.py:435-469` (`check_fire_barriers`)

`enrich` объявлен как `async def`, но вызывает **синхронные** функции без `run_in_threadpool`:

```python
terrain_type = sv.get_terrain_type(i.lat, i.lon)                      # :277  сеть (osmnx)
poly, cells_data = sv.hazard_polygon(...)                             # :281  CPU
radius_m = ros * burn_minutes                                          # :284
barriers = sv.check_fire_barriers(i.lat, i.lon, radius_m, poly)        # :285  сеть (osmnx)
```

`get_terrain_type` → `ox.features_from_point((lat, lon), dist=100)`, `check_fire_barriers` → `ox.graph_from_point((lat, lon), dist=radius_meters, network_type="drive")`. Оба — синхронные `requests`-запросы к Overpass (osmnx использует собственный таймаут `ox.settings`, по умолчанию 180 с — см. [документацию osmnx по settings](https://deepwiki.com/gboeing/osmnx/2.2-configuration-and-settings)). Асинхронный контекст их не спасает: пока Python ждёт сокет внутри синхронного вызова, **событийный цикл полностью заблокирован**.

Критично, что `radius_m = ros * burn_minutes` для леса — это **7 600–10 100 метров** (посчитано по `_FUEL`/`rothermel_ros`), то есть на каждый инцидент скачивается дорожный граф в квадрате ~15×15 км. В городской местности это десятки тысяч рёбер, по каждому из которых затем выполняется `road.geometry.intersects(fire_polygon)` (`services.py:453-457`).

**Последствия:**
- Создание одного инцидента (`POST /incidents/report`, `/incidents/manual`, `PATCH /incidents/{id}/location`, `POST /incidents/{id}/refresh`) **останавливает весь сервер**: не обслуживаются другие HTTP-запросы, не доставляются WebSocket-оповещения МЧС, не проходит healthcheck.
- Длительность — от секунд до минут (до таймаута Overpass) на каждый инцидент.
- При недоступности Overpass каждый инцидент всё равно ждёт полный таймаут, после чего результат молча выбрасывается (`except Exception: return []`, `services.py:467-469`).
- Те же синхронные блокировки дают вызовы SQLAlchemy (`db.query(...)` в `enrich`, `_classify_fuel_with_fallback` грузит **все 4781 населённых пункта** в Python и считает haversine в цикле — `main.py:236-243, 737-744`) и `cv2.imwrite` (`main.py:367-368`).

**Отдельно:** результаты обеих дорогих операций **не участвуют в расчёте зоны** — `terrain` и `barriers` только складываются в метаданные `hazard_geojson` (`main.py:320-326`). То есть платится максимальная цена за косметику.

**Исправление:**
- Обернуть `get_terrain_type`, `check_fire_barriers`, `hazard_polygon` и все синхронные DB-вызовы в `await run_in_threadpool(...)`.
- Либо (предпочтительно) вынести `enrich` в фоновую задачу (`BackgroundTasks`/очередь) — тогда запрос отвечает сразу, а WebSocket присылает обновление по готовности.
- Заменить `check_fire_barriers` на один дешёвый Overpass-запрос (`way["highway"~"motorway|trunk|primary"]` + `way["waterway"="river"]`) вместо `graph_from_point`.
- Кэшировать `get_terrain_type` (сейчас — некэшируемый вызов на каждый инцидент) и, если он не влияет на модель, удалить.
- Добавить индексы/предвычисление для поиска ближайших населённых пунктов вместо полного перебора 4781 записи.

## 4. 🟠 Высокий приоритет (P1)

### P1-1. Анонимная загрузка медиа с неограниченным расходом CPU

**Где:** `main.py:396-430`, `services.py:65-91`

`POST /api/v1/incidents/report` доступен **без аутентификации** (`user: User | None = Depends(current_user)`, `main.py:399`). Ограничение — `RATE_LIMIT_PER_MIN=10` на IP, но IP берётся из заголовка (см. P1-5).

Видео до 100 МБ (`MAX_UPLOAD_MB=100`, `client_max_body_size 200m` в nginx) анализируется покадрово: до `MAX_VIDEO_SECONDS × FRAME_SAMPLE_FPS = 60` инференсов YOLO. На CPU (macOS — заявленная целевая платформа README) это 5–15 с на кадр → **5–15 минут процессорного времени на один запрос**. Никаких квот на пользователя, лимитов на суммарный CPU или очередь нет.

**Исправление:** требовать аутентификации для загрузки видео; отдельный, гораздо более жёсткий лимит на видео; глобальный семафор на количество одновременных инференсов; лимит суммарного времени анализа.

### P1-2. Спам-тревоги и уведомление МЧС от анонимного пользователя

**Где:** `main.py:330-334` (`notify`), `main.py:396`

Любой анонимный посетитель, отправив картинку, на которой модель даёт ≥ 0,40, создаёт инцидент `PENDING_VERIFICATION`, и через `notify()` **всем подключённым лесничим и диспетчерам МЧС** уходит WebSocket-оповещение; при ≥ 0,80 — `CRITICAL_ALERT` только МЧС (и на фронте это ещё и звуковой сигнал, `App.jsx:15-21,77`). При обходимом rate-limit (P1-5) это неограниченный поток ложных тревог — «крик волк» в системе раннего обнаружения пожаров.

**Исправление:** порог/подтверждение для анонимных источников (например, анонимные детекции не эскалируют до `CRITICAL_ALERT`, а копятся в очередь модерации); дедупликация по гео/времени до отправки; отдельный лимит на количество оповещений в минуту.

### P1-3. `/incidents` отдаёт до ~100 МиБ JSON и до ~600 000 полигонов на фронт

`out(i)` возвращает **все** колонки, включая `hazard_geojson`, в котором до 2000 ячеек, каждая с 5-точечным полигоном, плюс геометрия барьеров. Замерено:

### P1-4. `YOLO_DEVICE=cuda:0` по умолчанию ломает запуск без GPU

### P1-5. Rate-limit обходится, backend-порт открыт напрямую

**Где:** `main.py:85-96`, `main.py:82`, `docker-compose.yml`

```python
fwd = request.headers.get("x-forwarded-for", "").split(",")[0].strip()
key = (request.url.path, fwd or (request.client.host if request.client else "?"))
```

Ключ строится по **клиентскому заголовку**. Через nginx он перезаписывается (`proxy_set_header X-Forwarded-For $remote_addr`), поэтому там подделать нельзя. Но `docker-compose.yml` публикует backend напрямую:

```yaml
ports: ["8000:8000"]
```

Обращение к `http://host:8000` минует nginx → `X-Forwarded-For` подставляется атакующим → **любой лимит (login 10/мин, register 8/мин, report 10/мин) обходится одним заголовком**. Плюс открытый `/docs`, `/uploads`, все неаутентифицированные эндпоинты.

Отдельно: `_hits = defaultdict(deque)` (`main.py:82`) — словарь ключей **никогда не очищается**; при подделке IP он растёт неограниченно (утечка памяти / DoS).

**Исправление:** не публиковать порт 8000 (только `expose`), оставить единственную точку входа — nginx; доверять `X-Forwarded-For` только от известных прокси (`--proxy-headers --forwarded-allow-ips`); периодически чистить `_hits`; в multi-instance — Redis.

### P1-6. Токен в `localStorage` и в query-string WebSocket

**Где:** `frontend/src/api.js:3-4,18-19`, `backend/app/main.py:207-208`

```js
get: () => localStorage.getItem('kedr_token'),
...
`${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.host}/ws/alerts?token=${tok.get()}`
```

Два следствия: (а) `localStorage` доступен любому JS на странице — при любой XSS токен уходит (в коде XSS не найдено: `dangerouslySetInnerHTML`/`innerHTML` отсутствуют, React экранирует — это плюс, но защита в глубину отсутствует); (б) токен попадает в **URL WebSocket**, а значит в access-логи nginx (`$request`), в историю и в заголовок `Referer` — долгоживущий (12 ч, `ACCESS_TOKEN_EXPIRE_MINUTES=720`) токен утекает в логи.

**Исправление:** передавать токен в первом кадре/подпротоколе WebSocket (`Sec-WebSocket-Protocol`), а не в query; хранить токен в памяти + `httpOnly`-cookie с `SameSite=Strict` (потребует CSRF-защиты); сократить время жизни + refresh-токены.

### P1-7. SSRF через `/incidents/rtsp`

**Где:** `main.py:433-448`, `services.py:73` (`cv2.VideoCapture(path)`)

`url` из тела запроса без валидации передаётся в OpenCV/FFmpeg. Роль требуется MCHS, но в сочетании с P0-1 (подделка токена) это даёт возможность заставить сервер обратиться к произвольному адресу, включая внутренние (`http://backend:8000/...`) и метаданные облака (`http://169.254.169.254/...`).

**Дополнительно:** `seconds` (`main.py:437`) фактически используется как **количество кадров** (`max_frames`), а не секунды — параметр вводит в заблуждение и не ограничивается `MAX_VIDEO_SECONDS`. Живой поток без таймаута: `cap.read()` может блокировать поток-исполнитель бесконечно (nginx отдаст 504 через 300 с, но поток останется занят).

**Исправление:** allow-list схем/хостов, запрет приватных диапазонов, жёсткий таймаут на чтение кадра, исправить семантику `seconds`.

### P1-8. Загрузка весов YOLO без проверки целостности (RCE)

**Где:** `main.py:43-54`

```python
with httpx.stream("GET", url, follow_redirects=True, timeout=300) as r, open(path + ".part", "wb") as f:
```

Файл `.pt` — это pickle. `ultralytics.YOLO(path)` загружает его, а десериализация pickle — **исполнение произвольного кода**. Здесь нет ни проверки контрольной суммы, ни подписи, ни ограничения размера, ни привязки к HTTPS-хосту; редиректы разрешены. Ошибка/подмена URL (или компрометация хостинга весов) → RCE на сервере.

**Исправление:** пиновать SHA-256 и проверять перед `os.replace`; хранить веса в образе/неизменяемом томе, а не качать на старте; использовать `torch.load(..., weights_only=True)`.

## 8. Тестирование, CI и воспроизводимость сборки

- **Покрытие.** Единственный файл тестов (`backend/app/test_core.py`, 105 строк) проверяет только чистую логику: пороги, геометрию зоны, классификацию топлива, маппинг инфраструктуры. **Нет ни одного теста** на аутентификацию/авторизацию, эндпоинты, WebSocket, дедупликацию CLEAR, загрузку файлов, PDF. То есть самые рискованные места (P0) не покрыты.
- **Запускаемость.** `pytest` не указан в `requirements.txt`; докстрока указывает несуществующий путь. Тесты «для запуска внутри образа» — но образа для тестов нет.
- **CI отсутствует** полностью (нет `.github/`, нет иных конфигураций пайплайнов).
- **Python-зависимости не зафиксированы**: `requirements.txt` почти везде использует `>=` (`fastapi>=0.111`, `ultralytics>=8.2`, `osmnx>=2.0`, …) — сборка невоспроизводима, обновление минорной версии `ultralytics`/`osmnx` может сломать прод без изменений в коде. Зафиксирован только `bcrypt==4.0.1` (осознанно, из-за несовместимости passlib 1.7.4 с bcrypt ≥ 4.1).
- **Фронтенд**: `package-lock.json` закоммичен и `npm ci` используется — это плюс. Но нет ESLint/Prettier/тестов, нет скриптов `lint`/`test` в `package.json`, нет проверки типов.
- **Логи Docker**: драйвер `json-file` без `max-size`/`max-file` при обилии `print()` → неограниченный рост логов.
- **`.dockerignore`**: `backend` исключает `uploads/images/*` — хорошо; `frontend` исключает `node_modules`/`dist` — хорошо. `.DS_Store` в git не попал (проверено) — хорошо.

## 9. Что сделано хорошо (чтобы не потерять при рефакторинге)

- **Секреты не утекли в git**: `.env` не в индексе (`git ls-files --error-unmatch .env` → ошибка), реальных ключей в истории нет, `.gitignore` закрывает `*.db`, `backend/uploads/**`, `backend/weights/**`, `.env`.
- **Пароли**: bcrypt через passlib, осознанный пин `bcrypt==4.0.1`.
- **SQL-инъекции**: весь доступ к БД через ORM; координаты приходят типизированными `float` (Pydantic), а не строковой подстановкой в Overpass-запросы.
- **XSS в React**: `dangerouslySetInnerHTML`/`innerHTML` не используются нигде; тексты из API рендерятся как текст; `infraPopup` собирается через `createElement` + `textContent` (`RuMap.jsx:150-158`).
- **JWT**: алгоритм зафиксирован (`algorithms=["HS256"]`) → нет algorithm-confusion; `OAuth2PasswordBearer(auto_error=False)` с явной проверкой роли.
- **Права**: роль никогда не принимается от клиента при регистрации (`main.py:160-170`); гражданин может менять только свои инциденты (`main.py:564-565`).
- **Регистрация**: обрабатывается конкурентная вставка (`IntegrityError` → 409, `main.py:173-177`).
- **SQLite**: WAL + `busy_timeout=30s` + `pool_pre_ping` — грамотно для встроенной БД.
- **Отсутствие выдуманной погоды**: явный `weather_fallback` и `(None, err)` вместо фейковых значений (`main.py:257`, `services.py:182-205`), и это даже отражено в PDF.
- **Идемпотентный сидер**, TTL-кэш внешних вызовов, параллельный сбор контекста через `asyncio.gather`, `run_in_threadpool` для инференса, `healthcheck` + `depends_on: service_healthy`, провенанс координат (`GpsSource`), поля `reviewed_by`/`reviewed_at`.

## 12. Итоговая оценка

| Область | Оценка | Комментарий |
|---|---|---|
| Архитектура | ⚠️ Требует переработки | Вся тяжёлая работа синхронна внутри async; состояние в процессе; нет очередей и миграций |
| Безопасность | 🔴 Неприемлемо для production | Подделка JWT, демо-креды в prod, SSRF, обходимый rate-limit, RCE-риск через веса |
| Корректность модели | 🟡 Средне | Заявленный Rothermel — упрощённая эмпирика; рельеф и барьеры не влияют; дым = огонь по порогу |
| Надёжность/эксплуатация | 🟡 Средне | Нет ретеншена, ротации логов, бэкапов, CI; healthcheck не проверяет зависимости |
| Frontend | 🟢 Удовлетворительно | Хорошая a11y-база и отсутствие XSS, но есть утечки, гонки и проблемы производительности |
| Документация | 🔴 Вводит в заблуждение | Минимум 8 расхождений с кодом, включая критичные для запуска |
| Тесты | 🔴 Недостаточно | Нет тестов на auth/API/WS; pytest не в зависимостях; CI отсутствует |

**Вердикт:** проект находится на уровне «работающий прототип с хорошей функциональной идеей», но **не готов к эксплуатации в качестве системы оповещения о пожарах**. Пять пунктов P0 блокируют любой публичный запуск; их устранение — примерно 1–2 дня работы и оно снимет основные риски. Остальное — планомерная инженерная работа по разделам 10–11.
